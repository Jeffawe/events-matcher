Data format

The matcher needs three things: who was in each event and what was owed, what was paid, and (optionally) the right answers so it can score itself. All of it is plain JSON.

The big picture

Think of a group trip. Several people shared costs: a hotel, a dinner, a taxi. Each cost is an invoice split between some of the people. Later, money arrives in a bank account, labelled only with whatever the sender's bank printed. The matcher works out who each payment came from and which invoices it paid.

You provideWhat it isNeeded?
Event filesOne JSON file per event: the people involved and the invoices, with how each invoice is split.required (at least one)
PaymentsOne JSON list of money received: sender name as the bank shows it, amount, time, and any memo.required
Answer keyThe true sender and links for each payment. Only used to score the matcher; never used to match.optional

Payments never name an invoice. That is the whole point: the matcher infers it from the sender, the amount, the timing and the memo.

Event files

One file per event, for example events/lisbon.json. The file's name doesn't matter.

FieldTypeMeaning
idtextrequiredA short unique id for the event, like "trip".
nametextrequiredWhat people call it, like "Lisbon weekend". Words in it help: a memo saying "deposit for lisbon" points at this event's invoices.
start_date, end_datedaterequiredFormat YYYY-MM-DD.
peoplelistrequiredEveryone in this event. Each is {"id": "ana", "name": "Ana Silva"}.
invoiceslistrequiredWhat was spent. See below.

People

  • id is any short unique text. The same id must mean the same person in every event, so someone who goes on two trips keeps one id.
  • name is the full name the way people would normally write it. Accents are fine (Chloé). The matcher compares names loosely, so it finds "Chloe M", "D. Patel" or "BEN CARTER".

Invoices

FieldTypeMeaning
idtextrequiredUnique across all events, like "t_hotel".
datedaterequiredYYYY-MM-DD. Payments are normally matched to invoices dated on or before them.
vendortextrequiredWho was paid, like "Hotel Alfama".
descriptiontextrequiredWhat it was for, like "Group dinner". Memo words are matched against the vendor, description and event name ("dinner", "taxi").
totalamountrequiredDollars, like "800.00". Must be more than zero.
shareslistrequiredWho owes what. See below.
notetextoptionalAnything you want to remember. Not used in matching.

Shares: how an invoice is split

Each share names a person (an id from this event's people) and exactly one of:

  • "percent": "25", a percentage of the total, or
  • "amount": "100.00", a fixed number of dollars.

You can mix the two on one invoice. People left out of the shares owe nothing on that invoice (the taxi in the example involves only two of the four).

Percent shares are worked out in whole cents. Each is rounded down, and any leftover cents go to the shares one at a time in the order you list them, so the shares always add up exactly. If the shares add up to less than the total (say 90%), the rest is reported as "unassigned"; if they add up to more, it is reported as over-assigned. Neither stops the run.

The payments file

One JSON list, usually payments.json, of money that arrived. Each entry:

FieldTypeMeaning
idtextrequiredUnique per payment, like "p1".
sender_nametextrequiredExactly what the bank shows, however messy: "BEN CARTER", "D. Patel", "MOBILE DEPOSIT", even other scripts.
amountamountrequiredDollars received, like "200.00". Zero or negative amounts are held for review, not matched.
timestampdate-timerequiredWhen it arrived, like "2027-05-10T09:12:00". Seconds are optional, and a bare date works. Payments are processed in time order.
memotextoptionalWhatever the sender typed. Often empty. Useful ones: "hotel", "cab 92 + cabin 360", "covering Chloé's share".

Include only money received. Lines that look like outgoing payments or requests (a memo starting "You paid…" or "requests…") and bank-alert duplicates ("Chase alert") are detected and held rather than counted.

Answer key (optional)

If you know the right answers, add a key and the page (or matchpay score) will grade the matcher against it. It is never used for matching.

{
  "payments": [
    {"payment_id": "p1", "payer": "ana",
     "links": [{"invoice": "t_hotel", "owed_by": "ana", "amount": "200.00"},
               {"invoice": "t_dinner", "owed_by": "ana", "amount": "100.00"}]},
    {"payment_id": "p7", "payer": null, "links": []}
  ]
}
  • payer is the person id who really sent it, or null if it can't be known (the right answer for a payment the matcher should hold).
  • links lists which invoice shares it should pay. owed_by can differ from payer when someone covers another person.

Conventions and rules

  • Money is dollars, written as text ("19.99") or a plain JSON number (19.99). Both give the same result. Amounts are rounded to whole cents. One currency per dataset; there is no currency conversion. No thousands separators ("1000.00", not "1,000.00").
  • Dates are YYYY-MM-DD; times are ISO 8601 like 2027-05-10T09:12:00.
  • Ids can be any non-empty text. Person ids are shared across events; invoice ids and payment ids must be unique.
  • Names are free text. Nothing about a sender needs to be clean. The matcher handles case, accents, initials, typos, swapped order, nicknames and extra words, and holds anything it can't be sure of.
  • Timing matters a little. A payment normally pays invoices dated on or before it. A memo that clearly names a later invoice or event (a deposit) can reach forward.
  • Nothing is guessed silently. Anything uncertain shows up under "Needs a person" in the report.

A complete example

A four-person trip with three invoices and seven messy payments. Download the files from the repo and load them on the test page (choose "Your own files", then select both files together):

  • trip.json (the event)
  • payments.json (the payments)

events/trip.json

{
  "id": "trip",
  "name": "Lisbon weekend",
  "start_date": "2027-05-07",
  "end_date": "2027-05-09",
  "people": [
    {"id": "ana", "name": "Ana Silva"},
    {"id": "ben", "name": "Ben Carter"},
    {"id": "chloe", "name": "Chloé Martin"},
    {"id": "dev", "name": "Dev Patel"}
  ],
  "invoices": [
    {
      "id": "t_hotel", "date": "2027-05-07", "vendor": "Hotel Alfama", "description": "2 nights, 2 rooms",
      "total": "800.00",
      "shares": [
        {"person": "ana", "percent": "25"}, {"person": "ben", "percent": "25"},
        {"person": "chloe", "percent": "25"}, {"person": "dev", "percent": "25"}
      ]
    },
    {
      "id": "t_dinner", "date": "2027-05-08", "vendor": "Casa do Peixe", "description": "Group dinner",
      "total": "240.00",
      "shares": [
        {"person": "ana", "amount": "100.00"}, {"person": "ben", "amount": "60.00"},
        {"person": "chloe", "amount": "40.00"}, {"person": "dev", "amount": "40.00"}
      ]
    },
    {
      "id": "t_taxi", "date": "2027-05-09", "vendor": "City Cabs", "description": "Airport taxi",
      "total": "60.00",
      "shares": [{"person": "ana", "percent": "50"}, {"person": "ben", "percent": "50"}],
      "note": "Only Ana and Ben took the taxi"
    }
  ]
}

payments.json

[
  {"id": "p1", "sender_name": "Ana Silva",      "amount": "300.00", "timestamp": "2027-05-10T09:12:00"},
  {"id": "p2", "sender_name": "BEN CARTER",     "amount": "200.00", "timestamp": "2027-05-10T10:40:00", "memo": "hotel"},
  {"id": "p3", "sender_name": "Chloe M",        "amount": "200.00", "timestamp": "2027-05-11T08:05:00", "memo": "hotel"},
  {"id": "p4", "sender_name": "D. Patel",       "amount": "240.00", "timestamp": "2027-05-11T18:30:00"},
  {"id": "p5", "sender_name": "Ana S.",         "amount": "30.00",  "timestamp": "2027-05-12T12:00:00", "memo": "taxi"},
  {"id": "p6", "sender_name": "Ben Carter",     "amount": "100.00", "timestamp": "2027-05-12T20:15:00", "memo": "covering Chloé's share of the dinner"},
  {"id": "p7", "sender_name": "MOBILE DEPOSIT", "amount": "30.00",  "timestamp": "2027-05-13T07:50:00"}
]

What the matcher does with it: "BEN CARTER", "Chloe M", "D. Patel" and "Ana S." are matched to the right people; Ana's lump $300 pays her hotel and dinner shares; Ben's memo "covering Chloé's share of the dinner" is checked by arithmetic (Ben's $60 plus Chloé's $40 is exactly $100) and split between them; and "MOBILE DEPOSIT" names nobody, so it is held for a person. Ben's taxi share is genuinely unpaid, so that invoice shows as partly paid.

Using your files on the test page

  1. On the test page, pick Your own files.
  2. Select all your files at once: every event file, the payments file, and optionally an answer key.
  3. File names don't matter. The page works out what each file is from what is inside it: a list of objects with sender_name is the payments, an object with people and invoices is an event, and an object with a payments list of payment_id entries is an answer key.
  4. Press Run the matcher. Nothing is uploaded; it all runs in your browser.

If something is wrong with your files, the page lists each problem in plain words, with the file and the item, instead of running.

Using a folder on the command line

The command-line tool reads a folder laid out like this:

my_data/
  events/
    trip.json        one file per event
    wedding.json
  payments.json
  expected.json      optional answer key
python3 matchpay.py run --data my_data --open

The same checks run first, so you get the same plain-language problems. The command-line version can also use an optional local language model for the hardest names, and has a review loop that remembers your decisions. See the README.

Common problems

The page says…What to do
not valid JSON (…, line 12)A missing comma, extra comma or unmatched bracket near that line. A JSON validator will point at it.
missing "vendor" (or description, id…)Add the field to that invoice. Every invoice needs an id, date, vendor, description, total and shares.
a share names person "x", who is not in this event's peopleAdd that person to the event's people, or fix the id's spelling.
needs exactly one of "percent" or "amount"A share has both or neither. Keep one.
invoice id "…" is also used in …Invoice ids must be unique across every event file. Rename one.
"timestamp" must look like 2027-05-10T09:12:00Use ISO format. A bare date like 2027-05-10 is accepted too.
"amount" must be a number of dollarsRemove symbols and separators: "200.00", not "$200" or "1,000.00".
No payments file foundSelect the payments list too. It must be a JSON list whose entries have sender_name.
Notes: "shares cover $108.00 of $120.00"Not an error. The invoice's split adds to less (or more) than its total. The report flags it.
Notes: "Person id … is … in one file but … in another"Not an error, but check it: one id should mean one person across events.
